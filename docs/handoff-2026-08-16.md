## Start here: set Xcode up before anything else

The previous session did a large amount of iOS work **without the Xcode MCP
ever being connected**, and did not notice. Do not repeat that.

`~/.claude.json` registers the server as `xcrun mcpbridge`. It bridges into a
**running Xcode process** over XPC, and with Xcode closed it dies immediately:

```
mcpbridge/MCPBridge.swift:32: Fatal error: MCP_XCODE_PID environment
variable not set and no running Xcode processes found
```

The trap is that the server's *instructions* still load into the system prompt
from config even though the process died, so it reads as connected while
exposing zero tools.

**A gate, not a suggestion.** Do these three things and paste the output of
each before writing any iOS code. An unverified belief that the tool is
connected is what produced the whole problem.

1. Open `ios/Coiny.xcodeproj` in Xcode and let it finish indexing.
2. Search your own tool list for `mcp__xcode__`. **Paste what comes back.** If
   it is empty, the bridge is not running and every claim below is unavailable
   to you; say so plainly rather than proceeding.
3. Enumerate what the bridge actually offers and write the list into this
   document. Nobody has done this. The ~20-tool list in circulation comes from
   blog posts, not from this machine, so treat any specific tool name below as
   a hypothesis until step 2 confirms it.

**Expect to drift back to the CLI.** `xcodebuild` and `xcrun simctl` work,
they are familiar, and they will get you a green result. That is exactly what
happened last session: the whole iOS surface was built and tested without the
bridge, and everything passed. The pull is not laziness, it is that the CLI
answers a question the tools also answer. Reach for the bridge for the
questions the CLI **cannot** answer, listed next.

### First assignment: use the bridge to find what the tests cannot see

The tests are green and the code still had defects. Three were found last
session **only by looking at a screenshot**, after a full suite, SwiftLint, CI
and the accessibility audits had all passed:

- An `AccentColor` asset that compiled into the bundle and was never read, so
  the tab bar stayed system blue while the diff looked correct.
- A paywall that no test had ever reached, whose first audit found four
  contrast failures and two Apple-required links with 15.7pt hit areas.
- A disabled button whose label had been faded into near-invisibility.

None of these are findable by reading code or by running tests. All are
obvious in a rendered image. **That is the class of defect this tool exists
for, and finding more of it is the job.**

Start with the surfaces nobody has ever seen rendered:

1. **Dark mode. Every screen.** Nothing in this repo has ever been viewed in
   dark mode. The entire `signal` / `signalFill` / `onSignal` contrast argument
   in `CoinyTheme` was settled by arithmetic, never by eye, and the numbers
   are tightest exactly there.
2. **The Alpaca and Kalshi positions rows** (#215). The `--ui-testing` fixtures
   do not populate those connections, so those views have never rendered at
   all.
3. **Onboarding**, start to finish.

For each: render it, look at it, and report what is wrong in a sentence
naming the screen and the element. Then fix it with a test that fails without
the fix. A screenshot is evidence; "it looks fine" is not, so attach the
image or the audit output.

If the bridge turns out not to expose preview rendering, say so and fall back
to the `ExploratoryCrawlTests` screenshot approach, which does work. The goal
is the finding, not the tool.

**Use it for** what the CLI cannot do: `RenderPreview` (SwiftUI preview to an
image, which beats a four-minute simulator UI-test cycle for design work),
`DocumentationSearch`, `XcodeListNavigatorIssues` (real diagnostics instead of
the SourceKit "Cannot find type 'API' in scope" noise), `ExecuteSnippet`.

**Never use it for** `XcodeWrite` / `XcodeUpdate` / `XcodeMV` / `XcodeRM`. This
repo is XcodeGen-managed: `ios/project.yml` is source of truth and `xcodegen
generate` regenerates the pbxproj, discarding anything Xcode wrote. Those tools
silently lose work here.

**Not for build or test either.** CI runs `xcodebuild`, and matching CI is what
catches what CI catches.

**The mode conflict, so it is not rediscovered:** simulator test runs still want
Xcode CLOSED (stale CoreSimulator state). Xcode-open and simulator-test are two
modes, not one setup.

## The pattern worth carrying forward

Five integrations, one defect shape: **the client reads the field whose NAME
sounds like the total, while the vendor splits the balance into several.**
Nothing errors, so nothing is noticed.

| Vendor | Read | Missed |
|---|---|---|
| Kraken | `.S/.M/.B/.F` suffixes | `.T` tokenized, and five fiats beyond USD/EUR |
| Kalshi | `portfolio_value ?? balance` | `balance` is cash and they ADD |
| Hyperliquid | `clearinghouseState` (perps) | `spotClearinghouseState` |
| Coinbase | `available_balance` | `hold` (pending transfers) |
| Alpaca | `/v2/account` equity | `/v2/positions` holdings |

Kalshi had a **passing test asserting the wrong behaviour**, which is why the
bug survived.

When touching any balance integration, the question is not "does this endpoint
return a total" but **"what else does this vendor split the balance into"**.
Read the contract, never infer from the endpoint name.

Two related traps: a `NaN` reaching a `numeric` column via `.toString()` stores
**NULL**, turning "could not price one token" into "worth nothing"; and a value
that cannot be sourced must be **excluded**, never counted as zero.

## Things I got wrong this session, so nobody re-derives them

- **Reported ten vendors publishing `llms.txt`. It is seventeen.** The six
  missed ones were missed because hostnames were guessed rather than looked up;
  `trading.kalshi.com` does not resolve at all. Always try the docs subdomain,
  the apex, and `www.` before concluding a vendor has none. And verify BYTES,
  not just status: `docs.alchemy.com/llms.txt` returns 200 at 472 bytes and is
  a stub.
- **Reported Kalshi backwards.** Claimed it ignored positions and a user with
  $0 cash and $4,000 of positions would see $0. The truth was the opposite:
  positions were counted and **cash** was dropped. Reading the endpoint name
  instead of the contract caused it.
- **Claimed staging was 503 and that merges never deploy.** Both were stale.
  Staging is healthy and merges do deploy.
- **Told Antoine the missing Sign in with Apple entitlement was why nobody
  could get past the sign-in screen on the simulator.** It is not. Simulator
  builds strip every entitlement requiring a provisioning profile, so Sign in
  with Apple cannot work there regardless. The entitlement fix (#211) is still
  needed for device and TestFlight.
- **Wrote a test that reimplemented the logic it was testing**, which would
  have passed with the production code broken. Caught and replaced with
  assertions against the real parser. Worth watching for.
- **Chased one accessibility audit failure through three wrong hypotheses**
  before probing it at `UICTContentSizeCategoryAccessibilityXXXL` and finding
  it was a false positive. The measurement is recorded in
  `ios/CoinyUITests/AccessibilityAudit.swift`. Measure before theorising.
