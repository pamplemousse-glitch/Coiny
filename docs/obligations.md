file:line on branch `fix/critical-backend-bugs`. External claims link the authoritative source.

requires. Where an obligation implies a measurable engineering target (timeouts, availability,
error budgets), the number and its verification method live in the engineering budgets document

## 4. Threat model

Built from the actual architecture: opaque bearer sessions, 3 route scopes, Plaid webhook as the
only push path, ~30 integrations of three shapes (webhook, user-triggered sync, live fetch).
The two cross-user exposures already found and fixed (D1 debug-session mint, D2 shared Coinbase
dev key) define the most dangerous class for this product: one user's financial picture shown to
another. The BOLA/IDOR sweep across all 45 tables came back clean per the context brief (every
`:id` route scopes by `userId`), so the residual cross-user risk lives in operator-level keys and
config drift, not query predicates.

## 5. Data lifecycle: collection, retention, deletion, portability

**Collection.** Identity: Apple/Google `sub`, email (AES-256-GCM encrypted at write,
`backend/src/store/users.ts:22`), display name (`backend/src/db/schema.ts:17-30`). Financial:
Plaid transactions including merchant name, amount, date, category stored plaintext-at-field-level
(`schema.ts:99-108`); cached balance scalars for ~20 sync integrations; OAuth tokens encrypted for
Coinbase, TrueLayer, Discogs, and others (`schema.ts:271-304,430-439`). Device: APNs tokens
(`schema.ts:110-117`). Collection is close to the minimum for the product; the one avoidable
item is storing full transaction rows if only aggregates drive the pet, a scope question for the
product spec, not this document.

**Retention.** There is none. No purge job, no retention policy, no scheduler at all in the
codebase (defect D3; grep for retention/purge over `backend/src` returns nothing). The Safeguards
Rule requires disposal of customer information within two years of last use unless retention is
justified ([314.4(c)(6)](https://www.law.cornell.edu/cfr/text/16/314.4)). Concretely: transactions
of a user who disconnected a bank two years ago must go. Not urgent at day 0; write the policy
sentence now ("transaction data retained while the linked item is active plus N days"), build the
job when a scheduler exists.

**Deletion.** `DELETE /api/account` exists and is honest about its mechanics: Plaid `itemRemove`
per item with failures logged and skipped so Plaid downtime cannot block the right to delete,
then a single `deleteUser` relying on 43 `onDelete: 'cascade'` FKs covering every child table
(`backend/src/api/account.ts`, `backend/src/db/schema.ts`). Gaps, in priority order: the iOS
client swallows deletion failure (`SettingsView.swift:86`); non-Plaid OAuth grants are not revoked
upstream; backups are not addressed in any user-facing text (no such text exists).

**Portability.** Nothing. No export endpoint, no data-access response. No law requires it today
(CCPA/GDPR thresholds and triggers not met). At UK launch it becomes a UK GDPR right with a
one-month response clock. A JSON dump endpoint of the user's own rows is cheap insurance and makes
DSARs a non-event; build it with the UK work, not before.

## 7. Open questions needing a lawyer, phrased as the questions to ask

1. "We aggregate consumers' financial account data via Plaid and display it back to them, free
   during TestFlight, later $99/yr. Are we 'significantly engaged in financial activities' and
