## The Xcode bridge

`~/.claude.json` registers the server as `xcrun mcpbridge`. It bridges into a
**running Xcode process** over XPC. **21 tools**, enumerated against Xcode 26.5.

**A gate, not a suggestion.** Call `XcodeListWindows` and paste the result
before writing iOS code. It is the only tool taking no arguments, and 19 of the
other 20 need the `tabIdentifier` it returns.

### Driving `RenderPreview`, which is the reason to bother

1. `XcodeListWindows` for the `tabIdentifier`.
2. `RenderPreview(tabIdentifier, sourceFilePath)` once. The path is
   project-relative: `Coiny/Views/HomeView.swift`.
3. Read `supportedPreviewVariantOverrides`. The group is **`"Color Scheme"`**,
   values **`"Light Appearance"` / `"Dark Appearance"`**. It also exposes
   **`"Dynamic Type"`** from `X Small` to `AX 5`, and `"Orientation"`.
4. Call again with `previewVariantOverrides`.

The first render includes a cold build, ~6.5 minutes; every render after is
15-25s. A first attempt may fail with `UpdateTimedOutError` and simply succeed
on retry.

**`SettingsView.swift` will not render.** Six attempts, including after a clean
`BuildProject`: always `TimeoutError: … thunk to build after 30.0 seconds`,
while `GetBuildLog` shows that same thunk **succeeding**. Not a compile error.
Undiagnosed. Use the crawl fallback for that screen.

### When the bridge looks dead

0. **Orphaned `mcpbridge` processes.** Every `/mcp` spawns one and they do not
   exit when the connection drops. Two orphans from previous days held the XPC
   connection and the fresh bridge timed out fetching tools
   (`MCP error -32001`). Fix: `kill` every `mcpbridge` pid, then `/mcp`. Exactly
   one should remain. Xcode does not need restarting.
1. Is Xcode running at all? With none, the bridge fatal-errors at launch and the
   client shows zero tools **while still loading the server's instructions**, so
   it reads as connected.
2. Is a modal open? Press Escape.
3. Is the probe itself broken? A hand probe that closes stdin makes the bridge
   exit before answering: zero bytes, no error.

Measured and cleared as non-causes, so do not re-blame them: Xcode indexing
(0.4% CPU) and SourceKit (0.0%).

**Closing Xcode ends the bridge for the session.** Reopening does not restore
it; only Antoine can, with `/mcp`. Simulator test runs still want Xcode CLOSED
(stale CoreSimulator state). So plan in two blocks — all bridge work, then all
simulator work — rather than alternating.

**Never** use `XcodeWrite` / `XcodeUpdate` / `XcodeMV` / `XcodeRM` /
`XcodeMakeDir`. This repo is XcodeGen-managed and `xcodegen generate` discards
whatever Xcode wrote.

## The lesson this session, which changes how to verify anything visual

**A test over colour tokens cannot see what the screen renders.** This produced
three separate false passes in one afternoon, twice on code written minutes
earlier and believed correct.

1. **`.disabled()` multiplies a label's opacity AFTER its colour is chosen.**
   #220 wrote *"a DIFFERENT PAIR of tokens, not the same pair at reduced
   opacity"* into `PaywallView` and left `.opacity(isEnabled ? … : 0.4)` in
   `CoinyFilledButtonStyle`. The "fixed" subscribe button shipped at **2.92:1**
   dark and **2.26:1** light. The comment was right and the code was not.
   **A comment claiming a fix is not evidence of a fix.**
2. **A contrast helper that ignores alpha** scored `Color.secondary.opacity(0.3)`
   well above AA; it renders at **1.41:1**.
3. **Compositing in the wrong colour space.** Core Animation blends the
   gamma-encoded components, not linear light. Blending linear predicts
   `#EBEBEB` and scores that border **4.01:1, a pass**; the screen renders
   `#D9D9DA` at 1.41:1.

`ios/CoinyTests/DarkModeRenderingTests.swift` is the harness. It renders a view
in a named scheme, measures pixels, and attaches every image it measured.
Three things it learned the hard way, all commented in place:

- Use **`drawHierarchy`**, not `layer.render(in:)`, which silently omits
  UIKit-hosted controls. `SignInWithAppleButton` was simply absent from the
  capture and the test measured the background behind it.
- Measure antialiased text and 1pt strokes by **percentile of luminance**,
  never most-common-colour. Glyphs have no dominant value: a count threshold
  picked a fringe pixel and reported 1.05:1 for a legible label. A 1pt stroke
  renders at ~60% of its token.
- Measure **both** sides. A token foreground against a measured background
  leaves the foreground unverified.

## The one vertical the audit does not cover

`docs/prelaunch-verification/` is thorough on security, privacy, interface
craft, performance, compliance and accessibility. Searched 2026-08-17, it has
**nothing** on the risks specific to **AI-generated code**, which is how most
of this repository was written.

The industry checklists converge on failure modes worth a pass here:

- **Hallucinated and squatted dependencies.** A 2025 USENIX study found 19.7%
  of AI code samples referenced packages that do not exist; attackers register
  those names. `CLAUDE.md` already says "no new dependencies without a reason",
  which is the right instinct; what is missing is a check that every dependency
  in the lockfile is the package it claims to be.
- **Authorization written per-route rather than centrally.** Coiny is in good
  shape here: `backend/tests/authorization-matrix.test.ts` enumerates routes
  from the built Fastify instance rather than a hand list, so a new route is
  protected by default. That is the control the checklists ask for.
- **Abandoned endpoints.** Vibe coding creates, modifies and abandons routes.
  `docs/openapi.yaml` documents **15 of 157 routes** and was last touched in
  May, so nothing enumerates the surface. Runbook rows A2/A3 depend on it.
- **Logs as a shadow database.** Covered: `.claude/rules/security.md` #2, and
  runbook G1.21 adds the pino `redact` array.
- **Confidence miscalibration.** The measured finding is that developers using
  AI assistants produce less secure code *and are more confident in it*. This
  session produced three concrete instances in one afternoon. It is the reason
  the rendering harness exists.

Sources: [Invicti](https://www.invicti.com/blog/web-security/vibe-coding-security-checklist-how-to-secure-ai-generated-apps),
[OX Security](https://www.ox.security/blog/vibe-coding-security/),
[Serenities AI](https://serenitiesai.com/articles/vibe-coding-security-checklist-2026).

## The CI toolchain: what is pinned, and what watches each pin

Derived 2026-08-17 by reading all 13 files in `.github/workflows/`, plus
`.github/dependabot.yml` and `backend/Dockerfile`. Recorded because it took a
search to assemble and evaporates otherwise, and because a green pipeline
cannot report its own staleness.

| Thing | Pinned as | Kept current by |
|---|---|---|
| GitHub Actions | SHA + version comment | Dependabot, weekly |
| `backend/` npm deps | lockfile | Dependabot, weekly |
| Xcode | major, `XCODE_MAJOR: "26"` | `toolchain-drift.yml`, weekly |
| macOS runner | `macos-26` | the drift job, implicitly |
| `ubuntu-latest` | floats | GitHub |
| Node | `'26'` in CI, `node:26-alpine` in the Dockerfile | **nobody** |
| pnpm | `11.1.3`, exact | **nobody** |
| Java | `'17'` | **nobody** |
| xcodegen, xcbeautify, swiftlint | **unpinned** | **brew, silently, on every run** |
| Docker base image | `node:26-alpine` | **nobody**, the docker ecosystem is not enabled |
| `shared/` npm deps | lockfile | **nobody**, only `/backend` is watched |

### The principle, because it is what was actually missing

**Pinning and currency are opposites and you need both.** Pin so a build is
reproducible and a bump is a reviewed change; then run something *unpinned, on
a schedule*, whose only job is to say the pin has aged. Nothing in a passing
pipeline will ever volunteer that it is ten majors behind, which is exactly
what happened: CI ran Xcode 16.x while development ran 26.5, every run green.

Three mechanisms are needed and only one and a half exist:

| Mechanism | Covers | State |
|---|---|---|
| Bot-raised PRs | anything a registry can enumerate | Dependabot, 2 of 5 ecosystems |
| Drift detection | what no bot manages: Xcode, runner images, brew | Xcode only |
| Pinning | anything that can change underneath you | the brew tools violate it |

### The three gaps, and the fix for each

1. **Dependabot is aimed at half the project.** It watches `github-actions`
   and `npm:/backend`. It does not watch the **Docker base image** the server
   actually runs on, so a CVE in `node:26-alpine` is never raised, nor
   **`shared/`**, which is live code. `mobile/` is dead and can stay unwatched.
   *Fix: two entries in `.github/dependabot.yml`.*

2. **Three tools install whatever is newest, on every run.**
   `brew install xcodegen xcbeautify swiftlint` carries no version. This is the
   inverse of the Xcode bug: those were frozen too hard, these are not frozen
   at all. The failure mode is a PR that was green this morning and red this
   afternoon with **no change to the repository**, because SwiftLint shipped a
   rule overnight. That is an hour spent hunting a bug that does not exist.
   *Fix, revised: do NOT pin them. Brew publishes no versioned formulae for
   these, and pinning would make CI more stale, which is the problem being
   fixed. Print the resolved versions into the job summary instead, so a break
   caused by a tool update is self-explaining rather than a hunt through your
   own diff.*

3. **Node's version is declared twice and never reconciled.** CI says `'26'`,
   `backend/Dockerfile` says `node:26-alpine`. Nothing compares them. If they
   drift, the suite proves something about a runtime production does not use,
   and everything stays green while it does.
   *Fix: one source of truth, or a check that fails when they disagree.*

## The next PRs, in order, and why each one matters

Found after the body of this document was written, from reading Plaid's
pricing and billing page. The first is a real defect that only appears in
production, which is the worst kind to find late.

### 1. The unlink path can orphan a billable Plaid Item

`backend/src/api/plaid-link.ts`, `DELETE /api/plaid/item`:

```ts
try { await itemRemove(item.accessToken) }
catch (err) { req.log.warn(…) }   // swallowed
await deleteItem(item.itemId)      // the token goes regardless
```

The comment says *"Unlinking is not blocked by Plaid being unreachable"*,
which is a reasonable UX call and is harmless in sandbox, where nothing
costs anything.

In production it means: **when `/item/remove` fails, we delete the only copy
of the access token while the Item stays alive at Plaid.** Plaid's billing
page is explicit that a subscription Item is charged monthly "even if no API
calls are made for the Item", that ending it requires `/item/remove`, and:

> "be sure to persist your access tokens and do not lose track of them… If
> you have created access tokens for which you are being billed but did not
> store the tokens, contact support for assistance."

So the failure mode is an Item billed every month that we cannot cancel
ourselves, and which has permanently consumed one of ten trial slots.

**Fix:** on `itemRemove` failure, keep the row, mark it (`revoked` status
already exists) and retry on the scheduler. The user-facing unlink should
still succeed immediately; it is the *row* that must outlive the failure,
not the user's wait. About an hour. **Do this before production Plaid.**

### 2. Trial Items are a permanent burn, and nothing in the code knows it

> "You can create 10 Production Items on a Trial plan… **Removing Items
> created on a Trial plan (using `/item/remove`) will not allow you to
> create more Items.**"

Ten links, forever. Unlink does not return the slot. Nothing in Coiny
counts them, and the natural testing loop — link, look, unlink, relink —
burns three.

**Fix:** at minimum, write it down where a tester will see it. Better, log a
warning when the item count for the environment crosses a threshold. This is
an operational constraint, not a bug, but it is the kind that is discovered
at slot nine.

### 3. Three subscriptions per Item start billing on upgrade

`linkTokenCreate` requests `transactions`, with `investments` and
`liabilities` in `required_if_supported_products`. All three are
subscription-fee products. The existing comment in `plaid/client.ts`
correctly explains why `required_if_supported_products` is better than
`products` — it bills only where the institution supports it — but predates
the trial, and Plaid states plainly:

> "If you add a subscription-billed product to an Item while on a Trial

No change is obviously required. The decision to make consciously is whether

### 4. `performAccessibilityAudit` is unreliable, and it is now blocking #231

Investigated 2026-08-17 and **not resolved**. Written up in detail because the
next session should start from the evidence, not from hypothesis four: the
handoff for 2026-08-16 records an earlier audit failure chased through three
wrong hypotheses that turned out to be a false positive.

**What is settled.** `macos-26` with Xcode 26.6 works. The project compiles,
**522 unit tests pass**, SwiftLint passes, and the major-pin logic selects 26.6
correctly. The toolchain bump itself is sound. Every failure on #231 is
`performAccessibilityAudit` and nothing else.

**The audit does not give the same answer twice.** Four runs of the same test
on the same simulator:

| Run | Result |
|---|---|
| CI, Xcode 26.6 | Contrast failure on `'$4,300.00'` |
| Local, Xcode 26.5 | Contrast failure on `'Debts'` |
| Local | A `dynamicType` issue on `'Bank'` |
| Local, twice, no diagnostics | `Audit failed to complete in time` (Code=-56) |

**The timeout predates the Xcode bump.** It is the identical error that failed
#226 on Xcode 16, where it was written off as flake. So the audit has two
separate problems and only one of them is new.

**One hypothesis is already ruled out, so do not spend time on it.** The helper
in `ios/CoinyUITests/AccessibilityAudit.swift` already excludes contrast issues
whose element intersects the tab bar. Measured on iOS 26 the tab bar frame is
`(0, 791, 402, 83)` and `'Debts'` sits at y=767.7 to 785.7, **just above** it,
so the exclusion correctly does not fire. Whatever washes out that text is not
the tab bar rectangle. Note iOS 26 draws a floating tab bar with a scroll-edge
effect above it; that is a candidate, and it is a candidate, not a finding.

**What is not settled:** whether a real contrast defect exists underneath the
flakiness.

**The recommended approach, because it does not depend on Apple's audit.**
`ios/CoinyTests/DarkModeRenderingTests.swift` renders a view in a named scheme
and measures pixels deterministically. Point it at the Wealth rows on an iOS 26
simulator and the contrast question is answered the same way every time. Settle

fix. Separately, make the audit retry once on `Code=-56` so a timeout stops
presenting as a finding.

**Do not let this gate the toolchain bump indefinitely.** CI sitting on Xcode
16 is the larger risk; that is what hid this for ten majors.

## The standard mobile-security checklist, mapped to this codebase

Antoine brought a nine-point mobile app security checklist on 2026-08-17. Every
point was checked against the code rather than answered from the list. Recorded
here because the same list circulates constantly and the answers should not be
re-derived each time.

**The short version: eight of nine are already handled, two of those by a
documented REFUSAL, and there is one real gap.**

| # | The checklist item | State here |
|---|---|---|
| 1 | Auth, short-lived tokens, server-side authz | **Covered.** Sign in with Apple (OIDC). `store/sessions.ts:6-7`: 30-day sliding TTL, 90-day absolute cap, row deleted rather than merely refused (audit 1.4.2, VERIFIED). Authorization is server-side and `backend/tests/authorization-matrix.test.ts` enumerates routes from the built Fastify instance, so a new route is protected by default. |
| 2 | Data at rest | **Covered.** iOS Keychain with `kSecAttrAccessibleWhenPasscodeSetThisDeviceOnly`. AES-256-GCM on Plaid access tokens, merchant names and recurring-stream descriptions. Investment transaction `name` is not stored at all, which is cheaper than storing it encrypted. |
| 3 | Data in transit, incl. certificate pinning | **Covered, and pinning is deliberately REFUSED.** HTTPS enforced, `fly.toml` sets `force_https`, HSTS in `plugins/security-headers.ts:61`, no ATS exception. Audit **1.12.1** refuses pinning quoting Apple's own guidance: *"In most cases, pinning is not necessary and should be avoided."* **1.12.2** costs the failure mode: a pin outlives its certificate only with a backup pin, and for a solo founder the failure is total and unrecoverable server-side. **Trigger to revisit: a written Plaid or partner requirement naming specific CAs.** |
| 4 | API hardening | **Covered.** `api/rate-limits.ts` exists; 33 API files validate with Zod; the authorization matrix above. |
| 5 | Session management | **Covered.** Two clocks (idle + absolute), `deleteOtherSessions` behind the Settings row, `MAX_SESSIONS_PER_USER = 10`, explicit sign-out clears the cache. |
| 6 | Anti reverse-engineering, jailbreak detection | **Deliberately REFUSED, audit 1.12.3.** Client-side integrity checks are defeated in minutes by Frida, which hooks the check itself. Everything worth protecting is behind a server-side session and the client is not the authority on entitlement. **Trigger: a fraud pattern a device-side signal would actually detect**, which for a read-only net-worth app does not obviously exist. |
| 7 | Error handling and logging | **THE REAL GAP.** `plugins/logger.ts` is 14 lines and has **no `redact` array**; it serialises `method` and `url` only. Errors are already handled well (`CoinyErrorLine` carries written copy, not `localizedDescription`), and `.claude/rules/security.md` #2 forbids PII in logs by policy, but nothing *enforces* it. Runbook **G1.21** is the fix and it is one hour: a pino `redact` array, `user_id` on the request line, `res.url` on completion. |
| 8 | Third-party SDK and dependency security | **Covered, with the gap already recorded above.** Semgrep, Trivy, Gitleaks, CodeQL and `pnpm audit` all run. The gap is coverage, not tooling: Dependabot watches 2 of 5 ecosystems, missing the Docker base image and `shared/`. See the CI toolchain section. |
| 9 | Continuous testing and maintenance | **Partial.** CodeQL and full-history secret scanning run on a schedule; static analysis is strong. **Nothing attacks the running system** — no DAST, no contract fuzzing, and `docs/openapi.yaml` documents 15 of 157 routes, which is what blocks both. Build order in `docs/testing-strategy.md` §7. |

### What to take from this

Two of the nine are **refusals with reasoning and a named trigger for
revisiting**, not omissions. If a future session or reviewer raises certificate
pinning or jailbreak detection, the answer is audit rows 1.12.1 to 1.12.3, not
a new investigation. Read them before agreeing to build either.

The one genuine gap is **logging redaction** (item 7), it is an hour, and it is
runbook G1.21. Everything else on the list either exists or is already
sequenced in `07-runbook.md`.
