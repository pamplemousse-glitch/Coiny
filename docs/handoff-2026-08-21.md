## 4. Next session: the broken-connection problem

**This is the brief. Treat it as research first and code second.**

### Why this and not more coverage

`market-research-2026-08.md` §3.1 finds the top reason people quit this
category is **broken connections, "by a distance"** — not missing asset
classes. §1.3 finds the core FIRE audience is spreadsheet-first and actively
distrusts integrations, having "spent more time nursing the integration than
actually watching my net worth". Competitor evidence agrees: Monarch's
most-cited complaint is connection reliability, not breadth.

So **every integration added expands the surface area of the number-one churn
cause.** Coverage is a real position, but it is not free, and reliability is
what retains people. Get this right before adding vendors.

The domain is unusually unforgiving for one reason: **a wrong number and a
right number look identical.** A failed image load is visibly broken; a failed
balance fetch is just a smaller number. And per the research, *"a visibly wrong
net worth breaks trust in the entire dashboard at once"* — not in that account,
in all of them.

### Start with a state-of-the-art sweep

Before writing anything, find out how this is actually solved. Search the
literature **and read real code**. Suggested ground:

- **Aggregator guidance itself.** Plaid, MX, Finicity and Akoya all publish item
  lifecycle and error taxonomies. Plaid has a support taxonomy dedicated to
  breakage. Read them as design input rather than as API docs
- **Open-source personal finance:** Firefly III, Actual Budget, Maybe Finance,
  Ghostfolio, Lunch Money clones. How do they represent a stale or broken
  account? What does the UI say? What does the schema store?
- **Resilience patterns and their libraries:** circuit breakers, bulkheads,
  retry budgets, hedged requests. Polly (.NET), resilience4j (Java),
  opossum (Node), Envoy's outlier detection. The patterns are older and better
  specified than most app code that implements them
- **Freshness and staleness as first-class:** stale-while-revalidate, SWR,
  TanStack Query's staleness model, CRDT/Delta-sync literature. The question
  "how does a client know how old this is" has good prior art
- **Consumer-facing precedent:** how do Monarch, Copilot, Kubera, Empower and
  Quicken actually SHOW a broken connection? Screenshot-level detail is useful
  here; this is a UX problem as much as a systems one

Write the findings up before building. A short survey document beats a
half-implemented pattern.

### The second question, which is the harder one

**How do we survive an API changing shape underneath us?**

This is not hypothetical here. Two instances this session alone:

- Polkadot moved balances to a different chain and the old endpoint kept
  returning `200 OK` with dust (#302)
- Zerion's `getPositions` needed pagination that nothing had noticed, so a
  large wallet would have been silently truncated (#295)

Neither produced an error. Both produced a plausible wrong number. **A schema
parse failure is the good case** — it is loud. The dangerous case is a response
that still parses and now means something different.

Research questions worth answering:

- **Contract testing.** Pact, Spring Cloud Contract, schemathesis, Dredd. Can we
  run vendor responses against a recorded contract in CI and fail on drift?
- **Recorded-fixture replay.** VCR, nock, Polly.js, MSW. We already vendor
  contracts in `docs/context/`. Could those be executable rather than
  documentation?
- **Canary accounts.** A known account with a known balance, checked on a
  schedule. If the answer changes when it should not, something moved. This is
  how the Polkadot bug would have been caught in a day rather than never
- **Invariant assertions on the data itself.** Not "did it parse" but "is this
  plausible": a balance that drops 99% overnight, a total that goes to exactly
  zero, a field that has been non-null for a year and is now null
- **Schema-diff monitoring.** Several vendors publish OpenAPI specs. Fetching
  and diffing them on a schedule is cheap
- **Deprecation and changelog watching.** Zerion, Plaid and Subscan all publish
  changelogs. Polkadot's migration was announced

Note the asymmetry that makes this tractable: **we do not need to auto-adapt.**
Auto-healing a changed contract is research-grade and probably unwise. Detecting
the change quickly, failing loudly, and degrading honestly is achievable and is
almost all of the value.

### What already exists, so it is not rebuilt

More than expected. Do not start from scratch.

- **`networth/classes.ts`** defines a nine-state vocabulary: `ok`, `stale`,
  `stale_excluded`, `error`, `disconnected`, `not_connected`, `pending`,
  `reauth_required`, `expiring`. Those distinctions are right. `pending` in
  particular ("connected, first fetch has not finished") is subtle and most
  apps show `$0` there
- **Per-class freshness policies** with two thresholds: `freshMs` (stops
  reading as current) and `excludeMs` (leaves the total). `excludeMs: null` for
  collectibles, because an old price beats a hole in net worth
- **A real connection lifecycle** on `plaid_items`:
  `healthy → expiring → reauth_required → revoked`, driven by webhooks rather
  than by waiting for a failure
- **`GET /api/net-worth` is a pure DB read.** A vendor outage cannot make the
  app slow or wrong, only stale. That is the cache-as-source-of-truth pattern
  already in place
- **`null` means unknown, `0` means empty**, now enforced across the chain
  clients (#289) and the Zerion path (#295)

### Where the actual gaps are

1. **Nothing tells anyone.** No error tracking, no alerting.
   `incident-response.md` says discovery would realistically come from a user or
   a researcher. A broken connection stays broken until someone notices
2. **No proactive repair.** The market research's own third defence — "detect
   breakage server-side and prompt" — is not built
3. **No drift detection.** Nothing would have caught Polkadot moving chains

### Suggested shape

1. SOTA survey, written up
2. Error tracking and alerting, because everything after it depends on being
   able to see failures. MetricKit is a system framework and adds no vendor to
   `service-providers.md`
3. Proactive connection health: detect server-side, prompt in-app
4. Drift detection: canary accounts plus invariant assertions, which is the
   cheapest thing that would have caught both bugs above
5. Only then, contract testing in CI if the survey says it earns its place

## 5. Standing instructions

- Push and open a PR for validated work without asking; **auto-merge on green
  CI** (`gh pr merge --squash --auto --delete-branch`)
- One logical chunk per PR. Do not batch
- **Run all three CI steps after the last edit**: `lint`, `typecheck`,
  `test:coverage`. Vitest transpiles without typechecking, so a green suite says
  nothing about types. This caught a real type error in a test file on
  2026-08-21 that the passing suite did not
- `test:coverage` at full local parallelism flakes on heavy PGlite tests
  (`compression`, `health-liveness`, `migration-journal`, `scheduler`), always
  with a 30-second timeout, always passing alone. `test:local` is the documented
  mitigation. **Do not conclude a failure is real without running it alone and
  baselining against `main`** — that mistake was made twice this session
- Never read or echo Keychain values
- **Before saying something does not exist:** check `prd.md`'s DR register,
  then `docs/context/`, then the vendor's own page, then the actual file. Four
  cheap checks. This session still produced two wrong claims that survived to
  the user before being caught, both from trusting a summary over a primary
  source
