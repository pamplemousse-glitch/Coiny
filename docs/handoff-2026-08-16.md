## Start here: set Xcode up before anything else

The previous session did a large amount of iOS work **without the Xcode MCP
ever being connected**, and did not notice. Do not repeat that.

`~/.claude.json` registers the server as `xcrun mcpbridge`. It bridges into a
**running Xcode process** over XPC, and with Xcode closed it dies immediately:

```
mcpbridge/MCPBridge.swift:32: Fatal error: MCP_XCODE_PID environment
variable not set and no running Xcode processes found
```

The trap is that the server's *instructions* still load into the system prompt
from config even though the process died, so it reads as connected while
exposing zero tools.

**A gate, not a suggestion.** Do these three things and paste the output of
each before writing any iOS code. An unverified belief that the tool is
connected is what produced the whole problem.

1. Open `ios/Coiny.xcodeproj` in Xcode and let it finish indexing.
2. Search your own tool list for `mcp__xcode__`. **Paste what comes back.** If
   it is empty, the bridge is not running and every claim below is unavailable
   to you; say so plainly rather than proceeding.
3. If step 2 comes back empty, see "When the bridge looks dead" below before
   concluding anything.

### How to actually drive it

Two mechanics that are not guessable and will waste a session if missed.

**Every call needs a `tabIdentifier`.** 19 of the 21 tools require it.
`XcodeListWindows` is the only one that takes no arguments, so it is always the
first call; everything else fails without the identifier it returns.

**Dark mode comes from `previewVariantOverrides`, not from editing code.**
`RenderPreview` returns three things: `previewSnapshotPath` (a PNG on disk,
which you then have to open and actually look at), `errors`, and
`supportedPreviewVariantOverrides`. That last one is a dictionary of variant
group names to the variants each supports. So:

1. `RenderPreview(tabIdentifier, sourceFilePath)` once, plainly.
2. Read `supportedPreviewVariantOverrides` from the response and find the
   colour-scheme group.
3. Call again passing `previewVariantOverrides` with the dark value.

All six main views have exactly one `#Preview` and **none** sets
`preferredColorScheme`, so without the override every render comes back light.
Do not "fix" that by editing six preview blocks; the override is the supported
path and leaves the source alone.

`previewDefinitionIndexInFile` selects which `#Preview` in a file, zero-based,
for the files that grow a second one.

### When the bridge looks dead

It probably is not. Three separate wrong diagnoses were made before the real
one, so check in this order:

0. **Are there orphaned `mcpbridge` processes?** This is now the first thing
   to check, because it is the one that actually happened next. Every `/mcp`
   spawns an `xcrun mcpbridge`, and **they do not exit when the connection
   drops**. Two orphans had been sitting there for days:

   ```
   $ ps -o pid,etime,lstart -p $(pgrep -f mcpbridge | tr '\n' ',' | sed 's/,$//')
   72465  02-21:59:39  Fri Aug 14 01:19:49   <- orphan
   28281  01-19:34:54  Sat Aug 15 03:44:34   <- orphan
   35777        01:36  Sun Aug 16 23:17:52   <- the one /mcp just made
   ```

   They still hold Xcode's XPC connection, so the fresh bridge connects and
   then times out fetching the tool list:
   `Reconnected to xcode, but fetching tools failed: MCP error -32001: Request
   timed out`. Fix: `kill` every `mcpbridge` pid, then `/mcp` again. Exactly
   one should be running afterwards. Xcode does not need restarting.

   Ruled out by measurement before landing on this, so do not re-blame them:
   Xcode was at **0.4% CPU** (not wedged) and SourceKit at **0.0%** (not
   indexing).

1. **Is Xcode running at all?** With no Xcode process the bridge exits with
   `Fatal error: MCP_XCODE_PID environment variable not set and no running
   Xcode processes found`, and the client reports zero tools while still
   loading the server's instructions, so it reads as connected.
2. **Is a modal open?** An Open Quickly box or a sheet can sit in front of the
   workspace. Press Escape.
3. **Is the probe itself broken?** This is the one that wasted the most time.
   A hand probe that pipes JSON-RPC in and closes stdin makes the bridge exit
   before it answers, returning zero bytes with no error, which looks exactly
   like a hung Xcode. Hold stdin open (a FIFO plus `exec 3> fifo`) and it
   responds in under a second.

Things that were blamed and were **not** the cause: Xcode still indexing, and
having many documents open in one Xcode window. Both were measured and cleared.

**Expect to drift back to the CLI.** `xcodebuild` and `xcrun simctl` work,
they are familiar, and they will get you a green result. That is exactly what
happened last session: the whole iOS surface was built and tested without the
bridge, and everything passed. The pull is not laziness, it is that the CLI
answers a question the tools also answer. Reach for the bridge for the
questions the CLI **cannot** answer, listed next.

## Disabled controls, and why a passing contrast test proves nothing

**A contrast test on colour tokens cannot see what the screen renders.** This
caught three separate things in one afternoon, so treat it as a rule.

**`.disabled()` multiplies a label's opacity AFTER its colour is chosen.** #220
wrote *"a DIFFERENT PAIR of tokens, not the same pair at reduced opacity"* into
`PaywallView` and left `.opacity(isEnabled ? … : 0.4)` in
`CoinyFilledButtonStyle`. `field` with `ink2` computes 6.29:1; the "fixed"
subscribe button rendered at **2.92:1** dark and **2.26:1** light and shipped
that way. The comment was right and the code was not, and nothing looked.

The fix is structural, not a better colour: a `ButtonStyle` owns its disabled
rendering completely, so swap tokens inside the style and delete the fade. It
is done, in `CoinyTheme.swift`, and now holds at all eight `.coinyFilled` call
sites. Two corollaries that were regressions until caught:

- Anything drawn *inside* a filled button must use `CoinyTheme.onDisabledFill`,
  not `onSignal`. `OnboardingPrimaryButton`'s spinner only ever shows while
  `isBusy`, which is the same condition that disables the button, so it was
  always on `field`: **1.06:1** in dark.
- `field` on `screen` is **1.08:1**, so a disabled button with no outline has
  no shape at all. Swapping the fill fixed the label and lost the control.

**Two more ways a green contrast test lied**, both now fixed in the harness:

- It ignored alpha, so `Color.secondary.opacity(0.3)` scored well above AA and
  rendered at 1.41:1.
- It composited in **linear light**. Core Animation composites the
  gamma-encoded components. Settled against a render rather than by argument:
  for that same colour on white, linear predicts `#EBEBEB` and scores 4.01:1, a
  **pass**, while the screen renders `#D9D9DA` at 1.41:1. Encoded predicts
  `#DCDCDD`.

`ios/CoinyTests/DarkModeRenderingTests.swift` is the harness for "does the
screen actually look right". It renders a view in a named scheme and measures
pixels, and attaches every image it measured. Three things it learned the hard
way, all commented in place: use `drawHierarchy`, not `layer.render(in:)`,
which silently omits UIKit controls like `SignInWithAppleButton`; measure
antialiased text and 1pt strokes by **percentile of luminance**, never by most
common colour; and measure **both** sides of a contrast pair, because asserting
a token foreground against a measured background leaves the foreground
unverified.

## The pattern worth carrying forward

Five integrations, one defect shape: **the client reads the field whose NAME
sounds like the total, while the vendor splits the balance into several.**
Nothing errors, so nothing is noticed.

| Vendor | Read | Missed |
|---|---|---|
| Kraken | `.S/.M/.B/.F` suffixes | `.T` tokenized, and five fiats beyond USD/EUR |
| Kalshi | `portfolio_value ?? balance` | `balance` is cash and they ADD |
| Hyperliquid | `clearinghouseState` (perps) | `spotClearinghouseState` |
| Coinbase | `available_balance` | `hold` (pending transfers) |
| Alpaca | `/v2/account` equity | `/v2/positions` holdings |

Kalshi had a **passing test asserting the wrong behaviour**, which is why the
bug survived.

When touching any balance integration, the question is not "does this endpoint
return a total" but **"what else does this vendor split the balance into"**.
Read the contract, never infer from the endpoint name.

Two related traps: a `NaN` reaching a `numeric` column via `.toString()` stores
**NULL**, turning "could not price one token" into "worth nothing"; and a value
that cannot be sourced must be **excluded**, never counted as zero.
