### What the finished prompt must contain

The same structure it has now, plus **embedded resource links**: a curated,
verified reading list the eventual PRD-writing agent can follow, organised by
category. Not a bibliography at the end. Links inline, next to the section that
needs them, so the agent reading section 3 finds section 3's sources there.

At minimum, find and verify authoritative sources for:

- **App development and launch checklists.** The exemplary GitHub repositories
  people actually use. Name them, link them, and say what each is good for.
- **Compliance with app-store and data-privacy law.** Apple and Google policy,
  GLBA and the FTC Safeguards Rule, CCPA/CPRA and the newer state acts, and
  whatever applies to a US consumer finance app that does not move money.
- **Security and cybersecurity.** OWASP MASVS control groups, MASTG test cases,
  Mobile Top 10 2024. Those three are already identified and grounded; find the
  rest, particularly anything fintech-specific.
- **Performance.** How iOS latency, cold start, frame rate and memory are
  actually measured, and what good looks like.
- **Interface craft and anti-patterns.** Sources on what makes an interface read
  as designed rather than assembled. `docs/design-direction.md` §3 is the
  in-house version; find the external ones.
- **Any category the research surfaces that is not on this list.** That is the
  point of doing the research rather than assuming the categories are known.

Every link verified as reachable, with one line on why it is worth reading. A
dead link or a listicle is worse than nothing.

### Then

Bring the rebuilt prompt back for review before running it. The eventual output
is `docs/prelaunch-verification.md`, a gate-by-gate checklist where every row
carries VERIFIED / FAILS / UNVERIFIED with evidence.

## Bugs found that were invisible until things were combined

Recorded because they are the pattern to keep watching for.

- **Migration journal ordering.** Drizzle silently skips an entry whose
  timestamp is below the last applied one. Four branches each picked a plausible
  value; merged, two sat below an earlier one. Worse, writing the guard revealed
  it had **already happened in production in June**: `0005_multi_user` and
  `0007_external_integrations` were never applied, and `0008_apply_missing_schema`
  exists to patch up what was lost. Now guarded by
  `backend/tests/migration-journal.test.ts` plus a CI rehearsal against a real
  production clone.
- **Five telemetry mismatches.** The server rejects unknown events rather than
  erroring, so the funnel would have looked wired and measured nothing.
- **A live R-9.5 violation.** Push was keyed on animation and the allowlist
  included `sad`, so a single overspend could push a phone.
- **Three timing-dependent tests** asserting machine speed, green locally and red
  in CI.
- **Three different Node versions** (local 26, CI 22, image 22). Nothing was
  testing what ships. That was the real cause of the undici mock failure, and
  the fix was one version everywhere, not a smarter mock.
- **The Fly release command never ran.** `ENTRYPOINT` ignored its arguments, so
  the release machine booted the server instead of migrating. Caught on the
  first deploy, and it failed in the safe direction: deploy aborted, old version
  kept serving, database untouched.
- **Merges fire no workflows.** Auto-merge completes via `GITHUB_TOKEN`, and
  GitHub does not trigger downstream workflows from that. The deploy workflow's
  own comment asserts the opposite. **Both staging deploys were dispatched by
  hand. This is unfixed.**

## Things I got wrong this session, so nobody re-derives them

- Said Fly deploys were manual. They are automatic on backend PR merge. I was
  repeating a stale note instead of reading the workflow.
- Said lint was clean when I had run biome from the repo root rather than the
  project's own script, which resolves config differently and hid real errors.
- Repeated "pre-existing lint errors" that four agents also asserted. `main` had
  zero. Nobody checked until late.
- Reported the suite green twice while CI was red, because I ran with reduced
  parallelism and CI does not.
- Claimed Trivy was passing when it had been reporting "skipping" for several
  commits due to path filters.
- Designated the existing app production when it has only ever held sandbox
  keys. The founder caught it.

The pattern: **verify with the project's own commands, under the same
conditions CI uses, and check the claim rather than the memory of it.**
